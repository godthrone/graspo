1.3 派生量与公式

  • 数据子集：subset_size（全局总条数）；prompts_per_rank = subset_size // cards（按卡视角）。
  • 每 epoch 优化步数上限：
    • SFT / CPT / OPD：floor(subset_size / cards)
    • GRASPO × ms-swift：floor(subset_size × G / cards)（G 为 rollout group size）
    • GRASPO × native：按 replay 阈值与每 epoch 末强制 flush 的真实调度口径计算（Q 为 rollout queue batch size）
  • 整个 run 的可达上限：expected_optimizer_steps_reachable = 每 epoch 上限 × max_epochs。
  • 不变量：checkpoint_save_steps > expected_optimizer_steps_reachable——否则会产出中间检查点，破坏「每档只保留一份检查点」。

2. 通过的定义

  • 判定单元 = 一行：模型 × 方法 × 模式 × backend × 并行维度。native 与 ms-swift 各记各的，不合并、不折算。
  • 通过：每个变体跑一次真效果训练；该次跑次同时满足「四条通用判据」（第 3.1 节）与该算法的「算法正确性检查」（第 3.2 节）⇒ 判 通过。
  • 不构成通过的情形：不取多数票；不用短跑或冒烟顶替；不以「跑通即通过」；不以「日志无异常」替代判据。

3.2 算法正确性检查（按算法各自设计，每条必须能失败）

graspo / SFT / CPT / OPD 各自出一份检查清单。每条检查同时满足三条硬约束：

  • 机核可跑：一条命令 / 一个断言即可判出结果。
  • 必须能失败：每条附阳性对照——注入一个已知错误，该检查必须 FAIL；构造不出失败对照的检查不得计入。
  • 标注齐全：离线可跑 / 需多卡 GPU、成本、归属层。
算法检查清单

3.3 效果基准与 B3：基础设施不应影响效果

  • 固定量（四者固定后才可比）：训练方法 × 基础模型 × 数据集 × 训练超参。
  • 不变量：基础设施层参数（并行度 / backend / 卡数 / 卡分配方式）怎么改，都不应显著影响效果。基础设施层一改效果就显著变化 = 缺陷信号，不是正常波动。
  • 基准的产生：单卡首跑 ⇒ 采集规定证据 ⇒ 结果经批准后，该次结果即基准。未获批准的跑次不得自称基准，也不得用它反推别档达标。
  • 达标门槛 δ：随基准一并冻结；此后 δ 不随跑次漂移；任何调整 = 新基准，须再次批准。

已验证不可用两条可用性判据中任一条未过。必须写明未过的是哪一条，并保留已通过项的事实——不得只写「失败」。
