# GRASPO 功能矩阵：需求 + 测试记录

> **本文件由两层组成**：
> **第一层 = 功能矩阵需求**（§2）：**本产品要实现什么**。列进去的每一项都是**实现目标**；"当前实现状态"只表示**进度**，
> **不代表它是否属于目标范围**。
> **第二层 = 测试记录**（§3–§5）：端到端实验跑出来的**实际能力**（每档最大可行上下文、实测显存、实测配方、状态、日期、产物）。
> **两层的关系**：**先写需求，再由端到端实验把实际能力补进来。**
>
> **为什么不让事前估算**：训练是"一事一例"的复杂工程——数据、长度、算子实现、通信、框架版本都会改变边界，
> **影响因素太多，事前无法估计"能做到什么"**。因此本文件**不做显存 / 上下文的推算或外推**；实际能力一律由实验测定后填入（§3）。
>
> **两条纪律**：
> ① **需求不因"当前未实现"而删**——未实现是**待补的目标**，只在"实现状态"里标进度；只有用户明确排除的才进 §2.7。
> ② **实测列只能由端到端实验填写**——禁止填写估算值、推算值或外推值。

## 2. 功能矩阵需求（本产品要实现什么）

> **本节全部是目标**。"当前实现状态"只标进度；**`⛔ 未实现（本期要补）` 的项同样是目标**。
> **用户已拍板的范围**（硬性）：`27B × 全量` 不做｜`CPT` `OPD` 仅 ms-swift、**LoRA 与全量均支持**｜`CP` 不加 native｜
> 8 卡不做｜**native 目标 = 并行 DP / TP / PP / SP，算法 SFT / GRASPO**｜**多模态是所有训练的目标**。

### 2.0 需求口径：以「分片 / 降显存方法」为单位，不以「支持哪个框架」为单位

> **本产品的需求是"能用哪些分片与降显存方法"，不是"支持多少个底层训练框架"。**
> - **方法才是需求**：TP、PP、CP、SP、ZeRO-1/2/3（优化器态 / 梯度 / 权重分片）、CPU offload、`l2k`、
>   `packing` / `padding_free`、梯度检查点、梯度累积 …… 这些才是 §2.4 要逐项落实的对象。
> - **框架只是手段**：DeepSpeed / FSDP2 / Megatron 都是**训练框架级别的策略**。
>   **不要求同时实现三套**——按"哪套能把方法做得最好"来选。
> - **优先依托 Megatron 引擎**：它对 TP / PP / **CP** / SP / 分布式优化器的支持最齐全，
>   且**是唯一能覆盖 CP 的路径**（CP 是长上下文的关键手段，见 §2.5）。
>   **⚠️ 该优先级的成立前提与当前证据档（声明层与事实层必须分开看）**：
>   ① **注册层 ✔**——官方受支持模型表的 `Support Megatron` 列对 `Qwen3.5-9B` / `Qwen3.8-27B` **均为 ✔**；
>      注册表实现在**外部包 `mcore_bridge`**（ms-swift 经 `get_model_meta` 查询，返回 `None` 即报 not supported）。
>   ② **运行时 ⚠️ 未验证**——**从未在这两个模型上跑过 Megatron**；既有 Megatron 实测只跑过 `Qwen3-8B`
>      ⇒ 本策略对目标两模型一律标为 **`⚠️ 官方声明支持，运行时未验证`**。
>   ③ **多模态强制 `mcore-bridge`**（`megatron-bridge` 不支持多模态，会直接报错），且需额外依赖
>      （`transformers>=5.0.0.dev`、`qwen_vl_utils`、`decord`）。
>   ④ **官方对 dense 模型推荐 transformers 后端**（Megatron 的推荐对象是 MoE）；且官方**无**
>      「`qwen3_5` dense 9B/27B + Megatron」现成脚本（Megatron 侧 `qwen3_5` 现成脚本只有 2B/4B dense
>      与 35B-A3B **MoE**；9B 在官方脚本里只作 teacher 出现）。
>   ⑤ **线性注意力（GDN）的 CP 官方要求 `megatron-core` main 分支**，测试节点装的是 **release 版** ⇒ 待确认。
>   ⑥ **备选回退路径**：若 Megatron 走不通 ⇒ ms-swift **标准路径 + SP（Ulysses / Ring，同样沿序列维分片）
>      + ZeRO-3**；native 侧用 **SP + TP / PP**。
> - **DeepSpeed / FSDP2 / device_map 作为补充**：仅在 Megatron 覆盖不到或成本过高时启用
>   （例如全量训练需要 ZeRO-3 + offload；以及多模态不兼容时的回退）。
> - **对外只有 `native` / `ms-swift` 两档后端**；**引擎 / 路径选择是 ms-swift 后端的内部实现策略，不暴露给用户做选择**。
>
> ⇒ 因此 §2.4 的表**按"方法"分行**，并给出每个方法在两后端的目标与当前实现状态；不按框架分行。

### 2.4 分片与降显存方法轴（**按"在配置里解决什么问题"分五层**）

> **为什么要分层**：这些方法**不是同一层级的东西**。`DP/TP/PP/SP/CP` 决定"卡怎么分"；
> 优化器态 / 梯度 / 权重分片与 CPU offload 是在**同一世界大小内**继续摊常驻状态；
> `GC/l2k/FA2/liger` **不改卡数分配**，只削峰值；`micro-batch/GA/packing` 决定"一次算多少"；
> 精度与拓扑是另一回事。把它们放进一张平表会让配置设计者无法判断**哪些选项能同时开、哪些互斥**。
> **本表是配置文件设计的输入**：每一行对应配置文件里的一个（组）字段，**层级对应配置文件的段落划分**；
> 具体的配置结构留待与用户讨论后确定（**本文档不发明配置文件格式，只写映射关系**）。
> **每行都从"方法"视角写目标与当前状态**；框架（Megatron / DeepSpeed / FSDP2）只出现在"对应配置项"与说明里。

#### **层 1 · 并行维度**（世界大小如何切分）

**这一层解决什么问题**：决定「卡怎么分」：把数据、权重、层、序列切到多卡。**这一层决定世界大小的分解方式**，是其余各层的前提。

| 项 | 作用 | native 目标 | native 当前 | ms-swift 目标 | ms-swift 当前 | 对应配置项 |
|---|---|---|---|---|---|---|
| **DP**（数据并行） | 把数据切到多卡；复制模型。native 为自研 all_reduce 实现（非 DDP） | **目标** | ✅ 已实现可跑 | **目标** | ✅ 已实现可跑 | `dp_size`（`schema.py:214`） |
| **TP**（张量并行） | 把权重的 hidden / 头 / FFN 中间维切到多卡。native 须整除注意力头数且 `TP ≤ num_kv_heads` | **目标** | ✅ 已实现可跑 | **目标**（依托 Megatron 引擎） | ⚠️ 引擎字段存在，通路未接通 | `tp_size`（`:213`）｜Megatron `tensor_model_parallel_size`（`:277`） |
| **PP**（流水线并行） | 把层切到多卡，多段流水。native 当前仅 `1F1B` 一种调度且多卡实测曾失败 | **目标** | ⚠️ 有入口未验证 | **目标**（依托 Megatron 引擎） | ⚠️ 引擎字段存在，通路未接通 | `pp_size`（`:215`）｜`pp_scheduler`（`:241`）｜`pp_micro_batch_size`（`:225`）｜`pp_max_inflight_microbatches`（`:236`）｜Megatron `pipeline_model_parallel_size`（`:280`） |

#### **层 2 · 分片策略**（权重 / 梯度 / 优化器状态如何摊）

**这一层解决什么问题**：在**同一世界大小内**把常驻状态再摊开：降低权重、梯度、优化器态的每卡常驻占用。**这不改变卡的分配方式**。**路线**：优先用 Megatron 引擎的分布式优化器与参数 / 梯度分片；DeepSpeed（ZeRO 预设 + CPU offload）与 FSDP2 / device_map 作为补充，仅在 Megatron 覆盖不到或成本过高时启用。**⚠️「Megatron 优先」的成立前提（声明层 ≠ 事实层）**：该优先级对**目标两模型**目前只有**注册层证据**（官方支持表标 ✔、注册表在外部包 `mcore_bridge`），**运行时从未实测**——既有 Megatron 实测全部跑在 `Qwen3-8B`（非混合注意力、非多模态）上。因此本层各项在 Megatron 引擎下的可达性，**须以 §2.8 G-12 的 1-iter 冒烟结果为准**；未过冒烟前不得按「已验证」使用。

| 项 | 作用 | native 目标 | native 当前 | ms-swift 目标 | ms-swift 当前 | 对应配置项 |

### 2.5 长上下文机制（**关键需求**）

> **长上下文必须依赖"序列维分片"（SP 或 CP），否则 OOM 风险极高。**
> - **序列维分片** = 把一条长序列按 token 维切开、分摊到多卡。**只有 SP / CP 属于这一类**；
>   **DP / TP / PP 都不切序列维**——加卡但不切序列，长序列的单卡占用不会下降。
> - **native**：序列维分片手段 = **SP**（保留实现，与 TP 同进程组，须 `TP ≥ 2`，不额外占卡）。
> - **ms-swift**：SP 已可用；**CP 是本期目标**，须依托其 Megatron 引擎接通（§2.8 G-5/G-6）。
>   CP **只切序列、不切权重**。
>   **⚠️ 目标模型的 CP 前提尚未闭合**：线性注意力（GDN）的 CP 官方要求 `megatron-core` **main 分支**，
>   而测试节点装的是 **release 版** ⇒ 待确认（§2.8 G-11）。若 Megatron 走不通，
>   **回退路径 = ms-swift 标准路径的 SP（Ulysses / Ring，同样沿序列维分片）+ ZeRO-3**；native 侧 = **SP + TP / PP**。
> - ⇒ 本节只规定"**必须靠什么机制**"；**每档实际能到多长由 §3 的方法实测**，不由本文件推断。

## 3. 测试方法

### 3.1 逐步加长到 OOM（定上限）

**目标**：对每一个目标档位（模型 × 算法 × 模式 × 后端 × 卡数），测出**该档能跑通的最长 token 长度**。

1. **数据量**（用户口径）：**SFT 每档 ≥ 100 条样本；RL 每档 ≥ 20 条样本**。数据量**不能太小**——太小看不出真实峰值。
2. **步数下限**：每档至少跑 **1 个完整 epoch** 且 ≥ **5 个 optimizer step**（`optimizer_steps ≥ 5`）。
   理由：仅 `≥2` step 只够触发优化器态分配，**显存峰值（激活 / 梯度 / 累积）需多步才稳定**，2 step 可能还没爬到峰值就结束了。
3. 从**基准长度 4K** 起，按档**逐步递增** token 长度（4K → 8K → 16K → 32K → 64K → 96K → 128K → …）。
4. 每一档都走 **A1–A6** 判定（§4.1）；**记录最后一个"因真实显存不足而失败"之前的通过长度**，即该档的**最大可行上下文**。
5. 递增在**首次出现"真实显存分配失败（OOM）"**时停止；若首次失败**不是 OOM**，则该档结果**无效**——须修复原因后重测（见 §3.2）。
6. **粒度细化**：64K 以上步长为 32K，可能跳过真实上限。规则：**在首次 OOM 点与上一个通过点之间做二分细化**（至少追加 1 个中间长度点），把该档上限收敛到更窄的区间；细化点也必须满足 §3.2 的失败分类要求。

### 3.2 失败分类（**只有真 OOM 才算能力上限**）

> **核心纪律**：§5.2 的「最大可行上下文（实测）」**只允许由"真实显存分配失败"界定**。
> 其他任何失败都**不得**写成该档的能力上限——它们是**缺陷**，须修复后重测。

| 失败类型 | 判据（如何识别） | 是否计入"最大可行上下文" | 处置 |
|---|---|:--:|---|
| **① 真实显存不足（OOM）** | 框架/驱动明确报显存分配失败（如 `CUDA out of memory`、`Tried to allocate … GiB`），且失败点是分配而非逻辑断言 | **是** ✅ | 该档上限 = 上一个通过长度；≥64K 时按 §3.1 第 6 条二分细化 |
| **② 框架未实现 / 不支持** | `NotImplementedError`、`ValueError`/`AssertionError` 由**合法配置组合**触发（如某机制与某模式不兼容） | **否** ❌ | 记 `❌ 失败` + 失败类型；作为**实现缺口**上报（§2.8），修复后重测 |
| **③ 配置非法** | 参数校验失败、互斥项同时开启、字段拼写/类型错 | **否** ❌ | 修正配置后**重跑**；**不得**记为能力上限 |
| **④ 数据问题** | 样本格式/字段缺失、tokenizer 异常、空样本、标签越界 | **否** ❌ | 修数据后重跑；记录样本号与原因 |
| **⑤ 通信与硬件** | NCCL/NVLink 超时、进程崩溃（SIGABRT/SIGSEGV）、设备不可用、被其他作业抢占 | **否** ❌ | 记 `❌ 失败` + 失败类型；排除环境因素后重跑 |
| **⑥ 数值异常** | loss / grad_norm 出现 NaN / Inf（见 A6），或梯度爆炸到非有限 | **否** ❌ | 记 `❌ 失败` + 失败类型；按 A6 处置，**不得**记为能力上限 |
| **⑦ 超时 / 未完成** | 在约定墙钟时间预算内未跑到判定点 | **否** ❌ | 记录实际运行时长；调整预算后重跑 |

**记录要求**：§5.2 的**备注列必须写失败类型**（用上表编号 ①–⑦ 标注）；只有 ① 才能写入「最大可行上下文（实测）」。

**为什么可以全测一遍**：**OOM 通常很快出现**（分配失败即退出，不需要跑完整个训练），因此"递增到爆"的总时间主要由通过档的运行时长决定。

### 3.3 运行记录元数据（可复现性）

每次运行至少留下：`exit code`、`optimizer step 数`、**失败类型（§3.2 编号）**、落盘 `ckpt`、`config` 快照、显存采样；
以及**环境指纹**：**代码 commit**、**镜像 tag**、**模型实物目录名**、**实际可见卡号范围**、**显存采样方式**、**数据集版本**。
以上一并填入 §5.2 的「产物」与「备注」列。

### 3.4 效果评测（SFT / GRASPO 的效果达标判定）

> **流程写死如下**，用于 §4.2 的效果判据求值；CPT / OPD 本期不判效果（见 §4.2）。

1. **初始模型锚点** = **训练前同一基座**（与训练档使用同一 `model_path` 与同一评测配置），记为 `acc_before`。
2. **训练后模型** = 该档训练产出的 checkpoint，记为 `acc_after`。
3. **评测集** = **ELAM V5 的 test 集**（与训练集同源、不重叠）。
4. **评测方式** = **同一 vLLM 评测流程**对两个模型各评一次（同一评测脚本、同一评测配置、同一评测集）。
5. **指标** = `reward 正确率`。
6. **判定式** = `Δ = acc_after − acc_before ≥ 20 个百分点`。
   **⚠️ 当前采用"绝对百分点"口径**（不是相对提升）；若用户口径为相对提升，按用户口径改。
7. **判定人** = 测试执行者产出**评测结果 JSON**；由**审查者复核**。

## 4. 通过标准

### 4.1 「跑通」判据 A1–A6（六条，缺一不可）

| # | 判据 | 判定方式 |
|:--:|---|---|
| **A1** | 进程成功 | `exit code = 0` |
| **A2** | 训练步真推进**且权重变化** | ms-swift：`global_step/max_steps: N/N`（N≥1）；native：`optimizer_steps ≥ 1`。权重变化二选一：LoRA ⇒ `lora_norm_delta ≠ 0`；全量 ⇒ 可训练参数 ≈ 全参 **且** 基座某层权重 L2 delta ≠ 0。**变化量必须 finite（非 NaN / 非 Inf）且非零** |
| **A3** | checkpoint **可加载** | 落盘 ckpt 存在 **且能被子进程重新加载**（不是只看文件在） |
| **A4** | 同 config 同 seed 两次一致 | 两次运行落盘产物 diff 为空（排除不可控随机性）；**对全部目标档位无条件适用**，每档跑 **2 次** |
| **A5** | 每档有落盘产物 | log / metrics / checkpoint / config 快照，四件套 + §4.4 的**环境指纹与评测产物** |
| **A6** | **数值健康** | 训练全程 `loss` 与 `grad_norm` **均为有限值（非 NaN / 非 Inf）**；且最终 `loss` 相比初始有下降趋势（不高于初始）。**阈值口径**：`loss`/`grad_norm` 出现任一 NaN 或 Inf 即 A6 不通过；梯度爆炸的量化上限暂按 `grad_norm ≤ 1e3` 判定，**该阈值待定**（不同模型/长度的合理量级不同，须由首轮实测标定后写死） |

**A4 的作用域与容差（可操作判据）**：
- **作用域**：A4 **只适用于"固定 config 的重复运行"**。在 §3.1 的递增流程中，**每个长度档一旦确定（通过或失败），该长度档再各跑 2 次**做一致性比对；**运行时不同 `max_length` 的两次运行不算 A4**。成本控制：长档（≥64K）可只对**最终确定的长度档**做双跑，中间长度档单跑（须在备注注明"中间档单跑"）。
- **一致性判据（可操作容差）**：
  - **必须逐比特一致的产物**：`config` 快照、数据集使用记录、`exit code`、`optimizer step 数`、失败类型。
  - **允许容差的产物**：`loss` 曲线**逐点相对偏差 ≤ 1e-3**；最终权重统计量（LoRA 权重或全量权重的 L2 范数）**相对偏差 ≤ 1e-4**。
  - **允许的非确定性来源**（须在备注声明）：CUDA 非确定性 kernel、packing 的动态 shape、通信归约顺序、混合精度累加顺序。
  - **最终容差阈值待定**：上列 `1e-3` / `1e-4` 为**初值**，须由首轮实测标定；标定前不得据此放宽 §4.3 的 L3 阻断判定。

### 4.2 「效果达标」判据（与「跑通」分层，两者都要过）

> **评测流程见 §3.4**（初始模型锚点 / 评测集 / 指标 / 判定式 / 判定人）。**判定式当前采用"绝对百分点"口径。**

| 算法 | 判据 | 口径与可执行性 |
|---|---|---|
| **SFT** | 测试集**综合准确率 ≥ 52.7%** | ⚠️ **该阈值是历史观测、非本期实测**，**基线配置 = `Qwen3.5-9B` + LoRA(r=128, α=256) + `TP1/DP4` 四卡 + mb1/GA4 + lr=8e-5/cosine + 3980 steps（10 epoch / 29.7 h）⇒ epoch9 = 52.7% / epoch5 = 45.7%**。**该基线与本矩阵各档【不同构】**（卡数与后端都不同）⇒ **不得当作同构判定**；本期各档须按 §3.4 自测 `acc`。阈值本身待用户拍板 |
| **GRASPO（RL）** | **`Δ = acc_after − acc_before ≥ 20 个百分点`** | `acc` = 同一 vLLM 评测流程在 **ELAM V5 test 集**上的 `reward 正确率`；`acc_before` = 训练前同一基座，`acc_after` = 训练后 checkpoint（§3.4）。判定人 = 执行者产出评测 JSON、审查者复核 |
| **CPT** | **本期只判「跑通（A1–A6）」，不判效果**；效果判据**待用户给定**。**用户已定：效果判据回头再议** | 标注为"不阻塞发布"（见 §4.5）；**维持「本期只判跑通、不阻塞发布」的现行处置** |
| **OPD** | **同上**（**用户已定：效果判据回头再议**） | 同上 |

> **CPT / OPD 不阻塞发布**：§4.5 的"效果达标"这一条**只对有判据的算法（SFT / GRASPO）求值**；
> CPT / OPD 档位**须显式标注"效果判据未给定"**，但**不影响发布判定**。
> **用户已定**：CPT / OPD 这俩**效果不好判定，回头再说** ⇒ 现行处置**维持不变**（只判跑通、不阻塞发布）。

### 4.3 验收深度 L0–L5（**与两套状态维度彻底分离**）

| 深度 | 内容 | 判据 | 是否阻断 |
|:--:|---|---|:--:|
| **L0** | 机制层（CPU、无 GPU、秒级）：纯函数与透传映射单测 | 测试通过 | 是 |
| **L1** | 启动层（GPU、分钟级）= A1 + A2 | `exit=0` + 真推进 step | 是 |
| **L2** | 产物层 = A3 + A5 | ckpt 可加载 + 落盘产物 | 是 |
| **L3** | 回归层 = A4，**宪法合规底线** | 同 config 同 seed 两次一致 | 是 |
| **L4** | 跨并行等价（单卡 baseline vs 各并行配置） | 趋势一致 | **否（增强层）** |
| **L5** | 跨后端等价（native ↔ ms-swift） | 趋势 / 包络一致 | **否（增强层）** |

> **正式验收深度 = L1 + L2 + L3**（CPT 只到 L1）；L4 / L5 不计入本期达标。
> **「通过」的定义 = A1–A6 全过**（本文件 §4、§5 各处"通过"均指此）。

### 4.4 每档产物契约（A5 / A6 的落地定义）

每跑完一档，其输出目录下必须齐备 **四件套 + 环境指纹 + 评测产物**：

| 类别 | 内容 |
|---|---|
| **四件套** | **① log**（完整训练日志，含启动参数回显）｜**② metrics**（逐步指标：step / loss / grad_norm / reward 等）｜**③ checkpoint**（训练产物，须能被子进程重新加载，见 A3）｜**④ config 快照**（该档实际生效的配置落盘副本） |
| **环境指纹** | **代码 commit**｜**镜像 tag**｜**模型实物目录名**｜**实际可见卡号范围**｜**显存采样方式**｜**数据集版本** |
| **评测产物**（SFT / GRASPO 必填） | **评测脚本**｜**评测结果 JSON**（含 `acc_before` / `acc_after` / `Δ` / **评测集版本** / **commit**） |

A4 的两次运行以**同一 config 快照 + 同一 seed** 执行，并**按 §4.1 的容差**做一致性比对。

### 4.5 发布判定

**全部目标档位通过 A1–A6（验收深度 L1+L2+L3）⇒ 跑通条件满足。**

**"效果达标"这一条只对有判据的算法求值**：
- **SFT / GRASPO**：须按 §3.4 与 §4.2 判定通过（SFT 阈值待拍板；GRASPO 为 `Δ ≥ 20 个百分点`）。
- **CPT / OPD**：本期**只判跑通（A1–A6）**，效果判据**待用户给定** ⇒ **不阻塞发布**，但**须在台账备注显式标注「效果判据未给定」**。

⇒ **本期目标达成 = 全部目标档位通过 A1–A6 + 有判据的算法（SFT / GRASPO）效果达标。**
